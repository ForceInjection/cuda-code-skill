### 1.5.2. Fixed-Point


Fixed-point emulation is used for emulating FP64 arithmetic and follows the [Ozaki Scheme](https://doi.org/10.1177/10943420241239588). Fixed-point representations emulate floating point through the addition of a shared power of two scaling factor and by encoding the remaining dynamic range of floating point within mantissa bits. The scaling factor is shared for elements in the same row of the A matrix or column of the B matrix and is used to logically scale all elements to be between -1 and 1 inclusively.


Due to the large dynamic range of FP64, there is no single configuration of fixed-point which is both performant and accurate for all floating point inputs. Therefore, we enable two flavors of fixed-point emulation: [Dynamic Mantissa Control](#dynamic-mantissa-control) and [Fixed Mantissa Control](#fixed-mantissa-control). These configurations can be set with [cublasSetFixedPointEmulationMantissaControl()](#cublassetfixedpointemulationmantissacontrol).


####  1.5.2.1. Dynamic Mantissa Control   
  
Dynamic mantissa control represents the cuBLAS library default mantissa control. Our automatic dynamic precision framework computes the proper number of fixed-point mantissa bits required to maintain equal or better accuracy than FP64. If the number of required mantissa bits exceeds a library defined default (see [Default Library Configurations](#default-library-configurations)) or a user provided maximum number of bits (see [cublasSetFixedPointEmulationMaxMantissaBitCount()](#cublassetfixedpointemulationmaxmantissabitcount)), the framework dynamically dispatches to native FP64.


####  1.5.2.2. Fixed Mantissa Control 

Fixed mantissa control can be leveraged to further accelerate fixed-point emulation. The user can provide the number of mantissa bits for the fixed-point representation via [cublasSetFixedPointEmulationMaxMantissaBitCount()](#cublassetfixedpointemulationmaxmantissabitcount); however, without the automatic dynamic precision framework, it is not possible to guarantee equal or better accuracy than FP64 arithmetic.


####  1.5.2.3. Representation and Mappings 

The fixed-point representation consists of a shared scaling factor for elements in the same row or column of a matrix, a sign bit, and mantissa bits. We store the sign bit and mantissa bits within 8-bit integers. Each matrix of 8-bit integers are referred to as a slice and the computational cost grows quadratically with the number of slices. The formula to convert mantissa bit count to slice count is as follows:

\\[\text{sliceCount} = \text{ceildiv}(\text{mantissaBitCount} + 1, 8)\\]

Note

The number of mantissa bits will always be rounded up to fully occupy the least significant slice


####  1.5.2.4. Fixed-Point Workspace Requirements 

When fixed-point emulation is used, the library requires workspace memory to store internal fixed-point representations and intermediate results. The amount of memory required depends on problem size, mantissa bit count, GPU architecture, and library version, but never exceeds 8 GB. It is recommended to set aside memory with [cublasSetWorkspace()](#cublassetworkspace), which can be used to guarantee [reproducible results](#results-reproducibility) and [improve performance](#fixed-point-performance-guide).


####  1.5.2.5. Fixed-Point Performance Guide 

Fixed-point emulation allows users to make performance and precision trade-offs for further acceleration. For dynamic mantissa control, users are able to configure the automatic dynamic precision framework to use fewer or more bits than the accuracy of native FP64 requires with [cublasSetFixedPointEmulationMantissaBitOffset()](#cublassetfixedpointemulationmantissabitoffset). Fixed mantissa control can be similarly tuned by increasing or decreasing the number of mantissa bits with [cublasSetFixedPointEmulationMaxMantissaBitCount()](#cublassetfixedpointemulationmaxmantissabitcount).

When the per-handle workspace is insufficient to meet the [fixed-point workspace requirements](#fixed-point-workspace-requirements), the library dynamically allocates additional memory with cudaMallocAsync(). This dynamically allocated memory is freed on stream synchronizations including [cudaDeviceSynchronize](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DEVICE.html#group__CUDART__DEVICE_1g10e20b05a95f638a4071a655503df25d), [cudaStreamSynchronize](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__STREAM.html#group__CUDART__STREAM_1g82b5784f674c17c6df64affe618bf45e), and [cudaStreamWaitEvent](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__STREAM.html#group__CUDART__STREAM_1g7840e3984799941a61839de40413d1d9). In cases where the number of invocations is too small to amortize the cost of memory allocation, or very frequent CUDA stream synchronization occurs, users can improve performance by:

  * Reducing the number of CUDA stream synchronizations

  * Manually managing memory and providing workspace with [cublasSetWorkspace()](#cublassetworkspace)

  * Allowing the [default memory pool](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY__POOLS.html) to retain memory between synchronizations


If cudaMallocAsync() fails to satisfy the request, the library falls back to non-emulated routines for affected calls. Providing workspace via [cublasSetWorkspace()](#cublassetworkspace) avoids both the allocation cost and the fallback path, and is required to guarantee [reproducible results](#results-reproducibility).

Note

`cudaMallocAsync` is not supported under CUDA in Graphics (CiG) contexts. In CiG contexts, provide workspace manually with [cublasSetWorkspace()](#cublassetworkspace) per the [fixed-point workspace requirements](#fixed-point-workspace-requirements).
